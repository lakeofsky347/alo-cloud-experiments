## 共同条件与系统身份

G1 Main 固定 `mimo-v2.6-flash`。G1 Strong 由业主于 2026-10-31 指定为 `mimo-v2.6-pro`。G2 使用 ALO，G3 使用原生 GroupChat，两者共享 M。候选池顺序固定为 `deepseek-flash`、`mimo-v2.6-flash`、`glm-5.3-flash`、`mimo-v2.6-pro`。正式合同绑定这些请求模型名，不能只记录逻辑角色名。

同题各系统的公共初态、工具权限、公开反馈来源及格式、资源规则可比。G3 保留原生自动选人、广播、恢复与停止机制；单轮一个 speaker 不表示单模型，不为均匀用量强制轮转。规划器、选择器、工作节点、验证、重试与失败全部计量。

## 数据与评价隔离

冻结具体数据 revision、题目 metadata、镜像 digest、原生评分器、公开检查和任务身份。每题先通过参考／独立源码正控、空候选、定向负控及评分完整性检查；镜像能启动不等于环境有效。

公开检查来自公开任务要求和允许的工具／参考程序交互。参考 patch、隐藏测试、私有期望值、终局分数和未来 probe 结果不进入作答输入或策略更新。不同题允许使用不同公开检查，同题各组使用相同生成规则。

所有作答终态封存后，关闭并清空对应模型凭据，再由独立评价器读取候选工件评分。Strong 的独立开发标签仅用于选定固定模型，不回流开发 agent 续答；正式评价和 probe 成绩不用于本轮超参数选择。

任务、模型、组别、阶段、节点、判据、策略、工件和资源记录具有独立身份。失败、基础设施未知、未启动和已知模型失败分开报告；unknown 不填零，不从计划分母移除。结果报告包含所有计划单位及未执行原因。

## Strong 开发选型

每轨三道开发题，每覆盖层一道；四候选在同样六道开发题各执行一次 B0，不做专属 B1，也不使用其他候选答案。候选和任务顺序事前冻结并配平。

对每候选分别计算 SWE 和 ProgramBench 三题的原生质量均值，按以下顺序选择：最大化两轨均值的较小值；再最大化两轨均值的等权平均；再最小化该候选本次开发单元的保守费用；完全相同则按候选池顺序。该合成键仅用于选型，不是跨基准总成绩，也不是逐题 oracle。

任一候选必要质量或费用证据缺失时，Strong 保持未选定；不能把未知当零或删除候选后宣布最强。Main 与 Strong 相同则合并运行与计费。选型费用比较只含本次候选开发单元，累计预算仍包含此前使用及未决预留。

2026-10-31 业主直接指定 G1 Strong 为 `mimo-v2.6-pro`，因此上面的开发集四候选 B0 不再执行。开发集选型本身会消耗本轮 200 CNY，而业主已决定把额度用于 M1/M2。`mimo-v2.6-pro` 是池内官方按量标价最高的模型，厂商中文模型页将其写成迄今最强的旗舰推理模型，用作固定的强单模型参照。G1 Main 仍是标价更低的 `mimo-v2.6-flash`。两者不同，运行与计费不合并。这不是六题开发集上的实测排序，开发题不进入本轮付费日程。

## M1 执行顺序

1. 冻结本轨六道任务、三或四个配置及执行顺序。每题每配置建立独立 B0 身份和干净工作区，不继承开发经验。
2. 在每条轨道内部按任务位置轮换配置顺序，各配置落在各位置的次数相差至多一。原生 GroupChat 内部的speaker选择不受该外层轮换修改。
3. 同题所有配置先独立完成或按合同终止 B0，封存工作区、完整原生会话、组织状态、随机状态及账本。
4. 按该题相同配置顺序，从各自 B0 检查点建立新的自身反馈 B1 身份。恢复完整本组状态，保留 B0 祖先关系和累计费用，不重放旧请求或覆盖终态。
5. B1 只接收本组合法公开反馈；不共享其他组代码、补丁或诊断。下一题恢复共同组织先验。全部采集结束并关闭凭据后独立终评。

主终点是 B1 原生质量。两轨各比较 G2−Strong、G2−G3；如给假设检验，四项属于同一 Holm 家族。每轨六题规模不支持充分功效的优效设计；主报告展示逐题配对原始分、平均差、资源和覆盖，保留仓库／任务族相关性。

## M2 学习、参考与 probe 顺序

每轨四道不同学习题和两道独立 probe，任务身份与 Strong／M1 不重叠；两条固定顺序、种子、首臂及probe配对顺序在学习结果出现前锁定。

1. **完成全部学习流。** 每条序列从共同先验开始，persist／reset 同题配对；按冻结首臂与题目位置交替执行顺序。persist 更新并向下一题传递白名单统计，reset 每题从共同先验开始。每条序列结束封存 persist 终态统计。
2. **执行固定参考。** G1 Main、G1 Strong、G3 对每轨四道学习题和两道 probe 各运行一次。Main／Strong 重合时合并；不人为添加 persist／reset 两臂，也不因两条顺序复制参考费用或样本。
3. **执行独立终态 probe。** 全部学习与固定参考结束后，每条序列的两道 probe 分别比较 learned-terminal 和 cold-prior，按冻结规则配平先后。每个 probe 从终态统计的一次性副本或共同先验独立启动，互不继承结果。cold-prior 不使用 reset 最后一题的题内后验。
4. **验证隔离并独立终评。** probe 前后源快照及 B／TMS／策略统计不变；一次性执行身份和审计写入不算学习更新。probe 输出不回写、不调参、不改顺序或停止点。对应采集凭据关闭后再独立评分。

允许跨题的状态仅为冻结模型／特征桶下的 B 后验、冻结主题下的 TMS 成败统计和声明数值质量／资源观测。源码、补丁、完整对话、角色身份、assignments、RNG、缓存、工件、原始反馈和隐藏分数不跨题传递。每条序列重新初始化，不导入 Strong 开发经验。

M2 主要对比为 G2 persist−reset，分轨报告。完整序列及任务家族相关，重复 probe 和序列位置不是新增独立题数；两条顺序只能支持有限范围的描述和估计。

## 能力信号与结论边界

本轮计划冻结的局部能力合同只验证**本节点通过显式 `write_file` 写入的 Python 源码语法**：控制器读取这些文件并调用 `compile()`，只有观察到 `SyntaxError` 才作可靠语法失败。具体文件读取、归因和语法验证器尚未接入本仓库的 sandbox；当前 adapter 仅消费由调用方显式提供的 `local_criterion` 结果，对可靠 pass／fail 更新 B／TMS。非 Python、无法归因的 shell 写入、规划／评审摘要、读取或基础设施错误均应保留 unknown，不能由实现方自报 pass 代替独立验证。

B／TMS 因而不等于功能能力估计，统计跨题迁移也不改变这一语义。全局公开质量、质量增量与资源预测独立记录、建模，不复制为最后节点的二值能力真值；质量伪后验不是客观 Bernoulli 能力 B。要声称功能能力学准，需另行冻结可靠局部判据和归因，或收窄结论。

ALO 在一次任务开始生成 DAG，当前按固定拓扑顺序串行执行；不因图或接口名称假定有执行中重写 DAG、并行节点或全局最优调度。B 后验变窄、TMS 累积或B0→B1改善均不能单独证明因果学习收益。

| 单元 | 请求 | tokens | 工具 | 墙钟秒 | 单命令秒 | 输出参数 |

| Strong 开发 B0 | 32 | 900000 | 120 | 1200 | 60 | 16384 |
| M1 B0 | 32 | 900000 | 120 | 1200 | 60 | 16384 |
| M1 自身 B1 | 16 | 900000 | 120 | 1200 | 60 | 16384 |
| M2 学习／probe／固定参考 | 32 | 900000 | 120 | 1200 | 60 | 16384 |

每模型累计 50 CNY、四模型共 200 CNY，包含失败与未知预留，跨批次不重置、不挪用。本仓库没有可引用的数值期初占用；历史 Drive 原件不在检出中且含模型回答，不导入。业主因此把本轮付费账本的期初承诺定为 0。账本文件写到运行目录之后，恢复运行继续使用同一文件，不把已发生的扣费清零。派发前按官方标价预留单次上限：提示按缓存未命中、补全按 `max_completion_tokens`，不足 1 microcny 的零头向上取整；没有缓存命中拆分时，全部输入按缓存未命中计价。`deepseek-flash` 采用官方高峰标价，避免高峰时段的实际账单高于预留。开发平均费用不代替最坏情形可行性；全部角色、反馈及验证开销均计量，token合同明确输入、输出、reasoning与缺失语义。

2026-10-31 业主决定了两项请求参数，详见[模型清单](models_and_benchmarks.md)：MiMo 按量请求只发送 `max_completion_tokens`（官方字段已经包含可见输出和推理 token，不再并送 `max_tokens`）；GLM-5.3-Flash 发送 `thinking.type=enabled`。账本里的 tokens 只记 `total_tokens`，并且该值必须等于 `prompt_tokens + completion_tokens`。`reasoning_tokens` 可以出现在 `usage` 顶层，也可以出现在 `completion_tokens_details` 里；两处同时出现时必须相等，并且小于等于 `completion_tokens`，不能再加一次。明细缺失时不把 reasoning 记成测得的 0，但 completion 里已经包含的用量仍算进 tokens。采样、`reasoning_effort` 和 `clear_thinking` 这次没有一起决定。

四个模型的补全上限都包含推理。调用方要求至少 4096 时，实际发送并预留 16384，避免推理写满 4096 或 8192 后可见内容为空。费用投影按实测均值抬高后的 18000 输入和 4096 输出估计，不把 16384 当成每次都会用满。供应商读超时与沙箱的 60 秒分开：MiMo-Pro 600 秒，其余模型 300 秒。这是整次请求的墙钟上限，流式保活或零星字节不能把同一次请求延长过这个上限。超时按该次预留的最坏金额结算，单元自动从头重启一次，日程继续；未知结果累计超过 3 次才停止整个日程。同一次重启只继承 CNY，不继承上一次尝试已经用掉的请求、token 和工具次数。

派发前预留。一次结果按三类处理，不再把它们合成同一种 unknown。HTTP 200、usage 自洽、但 `content` 为 null 或空字符串，是已知的计费完成：按供应商报告的 usage 用 `charge_microcny` 结算；`finish_reason=length` 且可见文本为空时，代理循环记一次空回答并停止该轮（length stop），不把预留留成 unknown。非 200 且响应体是可解析的供应商错误时，按 0 结算：三家价格页按成功产生的 token 计费，错误响应不另计；诊断文件仍留下错误码和消息。只有发送之后超时、响应中途连接被重置、以及无法解析的 HTTP 200，才保持 unknown，预留不释放，并停止后续派发。每种非成功完成都把脱敏诊断写到运行目录的 `diagnostics/<request_id>.json`（原因、HTTP 状态、供应商错误码和消息、不含请求头和密钥的响应 JSON、延迟、finish_reason）。认证头和密钥不写入该文件。

业主授权的恢复规则：基础设施或 unknown 打断的单元可以从头重跑一次。此前已经计入账本的花费保留，不从模型累计里删掉；工作区、检查点和日程记录归档，请求号带上重启代次，避免和旧预留冲突。单元记录写下 `restart_count`。第二次再被 unknown 打断时，该单元记为 blocked，不再重启。操作命令是 `python -m alo_cloud.ledger resolve`。把已经跑过的单元整批归档后再跑时，`archive-finished` 或 `new-epoch` 把运行目录的协议代次加一，并清掉这一代的重启计数。新请求号是 `req-e<代次>-<单元>-...`。旧代次的请求号不再被当成半截重试。账本里已经结算的 CNY 仍计入每模型 50 CNY 和合计 200 CNY。配对任务块无法共同满足预算时停止并保留未启动单位，不将后执行系统单方面受限解释为算法差异。
